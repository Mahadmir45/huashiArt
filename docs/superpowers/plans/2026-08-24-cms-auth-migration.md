# Hua Portfolio — Secure Shared CMS Migration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the hardcoded client-side admin password and per-browser `localStorage` content with real invite-only authentication (Netlify Identity) and server-shared content storage (Netlify Blobs), and rename the project to `hua-portfolio`.

**Architecture:** Move hosting from GitHub Pages to Netlify. Two small Netlify Functions (`get-content`, `save-content`) sit between the existing vanilla-JS frontend and a Netlify Blobs store holding the site's content JSON. Netlify Identity replaces the hardcoded username/password; `save-content` checks the authenticated user's email server-side against an `ADMIN_EMAIL` environment variable before writing.

**Tech Stack:** Vanilla JS/HTML/CSS frontend (no build step, unchanged). Netlify Functions (ESM, Node runtime) using `@netlify/blobs` and `@netlify/identity`. Tests via Node's built-in `node:test` — no new test framework dependency.

**Spec:** `docs/superpowers/specs/2026-08-24-cms-auth-migration-design.md`

## Global Constraints

- No password or shared secret may appear in any committed file, ever again (spec Goal 2).
- The public page must render correctly even if the backend functions are unreachable or storage is empty — always fall back to the bundled defaults already in `app.js` (spec: Data flow §1, Error handling).
- Only one authorized editor: the email in the `ADMIN_EMAIL` environment variable, never hardcoded (spec: Architecture, Authentication).
- No new frontend build step or bundler — `index.html`/`app.js`/`styles.css` stay plain, browser-loaded files (spec: Goal 5).
- Final live URL: `hua-portfolio.netlify.app`; GitHub repo renamed to `Mahadmir45/hua-portfolio` (spec: Rename & deployment).

## Implementation Note (deviation from spec wording, intentional)

The spec's Error Handling section describes `get-content` "returning a bundled default content object" on empty/failed reads. This plan instead has `get-content` return an empty JSON object (`{}`) in those cases, and lets the **frontend** merge that with its own existing `defaultContent` object — exactly the same merge pattern the current `loadContent()` already uses for `localStorage`. This satisfies the spec's actual requirement (the site never breaks, defaults always apply) without duplicating ~150 lines of content data into the serverless function as a second copy that could drift out of sync. Flagged here so this isn't mistaken for an oversight.

Create `netlify/functions/lib/save-content-handler.js`:

```javascript
export function createSaveContentHandler({ getStore, getUser, adminEmail }) {
  return async function handler(req, context) {
    if (req.method !== "POST") {
      return new Response("Method Not Allowed", { status: 405 });
    }

    const user = await getUser();
    if (!user) {
      return new Response("Unauthorized", { status: 401 });
    }
    if (user.email !== adminEmail) {
      return new Response("Forbidden", { status: 403 });
    }

    let content;
    try {
      content = await req.json();
    } catch (_err) {
      return new Response("Invalid JSON body", { status: 400 });
    }
    if (!content || typeof content !== "object" || Array.isArray(content)) {
      return new Response("Invalid content shape", { status: 400 });
    }

    const store = getStore("hua-portfolio-content");
    await store.setJSON("content", content);
    return Response.json({ ok: true });
  };
}
```
